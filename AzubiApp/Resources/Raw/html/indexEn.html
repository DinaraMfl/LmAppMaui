Auto-Store Procedure

In an Auto-Store procedure, units are defined that are used for orders instead of optimization units. These units are scheduled as a combination depending on the quantity required.

Example:

If a defined unit is exceeded, the next higher unit is used instead of a multiple of the previous unit.

Requirements:

  • The units should increase in size from top to bottom (SU0 -> SU?)
  • Range between units should increase with increasing BE line
  • Each unit should have an OU-Box ticked
  • None of the units should have a Mix-Box ticked

Auto-Store Procedure with Max. Coverage

If the order quantity exceeds the Max. Coverage, it will be rounded down to the largest possible OU

If a supplier unit is defined, it is used as the order unit

Example:

[Forecast: 5 Unit/Month | Max. Coverage: 3 Months]

With a required quantity of 8.20, 11 items are ordered instead of 20 (8 + 3)

[+ Supplier Unit: 10 Units]

The order quantity is adjusted to the SU (ticked box). This means that the 11 items are reduced to 10, as 20 items (2*10) would exceed the maximum range.

Stock Transfer

A stock transfer is a transfer of stock between warehouses/stores with the same item. More specifically, SKUs with missing stock are saved from an OoS situation by deliveries of SKUs with excess stock.

This delivery is called a stock transfer order and is carried out by a stock transfer supplier.

To determine whether a stock transfer is appropriate, the quantities that can be received and issued for both warehouses/SKUs are also calculated.

  • The receiving SKU is used to calculate the missing quantities.
  • The exceeding quantities are calculated for the delivering SKU.

If this calculation shows that the incoming or outgoing quantity is still not enough, for example, because the excess quantity is not large enough to make up for the missing quantity, the stock transfer order is canceled.

If several SKUs have a missing quantity, the SKU with the smallest missing quantity is preferred.

If the missing quantity is identical, the SKU with the latest availability date is selected.

In the event of a confirmed stock transfer, a reservation is created for the stock transfer SKU.

To activate stock transfers, adjustments must be made to the LOGOMATE system. Please contact your LOGOMATE contact person for further information.

Container Optimization

A container optimization determines a cost-effective container combination for a calculated (trigger) quantity and, if necessary, the rounding up of this container optimization. [Parameters -> Replenishment-> Quality criterion]. 8.5/8.6

In order for container optimization to be used, the quality criterion in the Compound group [Parameters -> Replenishment-> Quality criterion] must be set to “Container optimization”.

Setting in the parameters

These are also created in the conditions Conditions -> Units -> Conditions Quantities/ Prices/ Costs.

Setting in the conditions

If LCL containers are also to be considered, an additional line must be added under “Quantities, prices, costs”:

LCL stands for “Less than Container Load” and refers to a shipping method in which several shippers (suppliers) share one container.

Here, “gross vol.” must be selected as the reference. In addition, as above, the mix flag must be set and either “Additional supplier costs” or “Additional own costs” selected.

After filling, the total order is divided between the individual containers according to the previously determined optimum container combination. This is done as follows:

  • If an LCL container is included in the container combination, the order items are sorted by descending density and loaded into the LCL container one after the other until the intended volume is reached.
  • The order items and containers are sorted according to a suitable criterion, for example by density or possible residual density. [Selection of the optimum criterion see sort criterion in REMIRA Wiki].
  • The order items are then distributed to the containers either by optimization unit or - if possible - by bin location.
  • After each assignment, the remaining density of the container is calculated and the order of the containers is adjusted accordingly.
  • If an item no longer fits into a container, the container with the smallest overrun of the permitted volume is selected. If a storage space restriction must be observed, exceeding the weight limit is considered less critical than exceeding the storage space capacity.

Split-Condition

A split condition is used to distribute a Compound Order among several transporters if the order does not fit into one transporter because it is too heavy or too large.

There are a total of 4 different split methods, which can be set using “flags” (from 8.8-01 using “criteria”):

  1. Split as full as possible = one transporter is filled to the maximum and the rest goes into an additional transporter
  2. Split as evenly distributed as possible = all transporters carry the same quantity
  3. Split as single variety as possible = identical SKUs are kept together
  4. Reduce down according to coverage = The SKUs with the highest coverage are distributed to another transporter until the order fits into the first transporter.

The condition is set in the conditions under the “Quantity, Price, Costs” tab.

Before version 8.5-01: “Maximum limit per order” (only reducing down possible, without order with 2nd transporter)

From version 8.5-01: “Split to mixed (Opti) Unit” (“Reduce down according to coverage” not possible)

From version 8.8-01: “Maximum limit per order” (all methods possible)

Filter(classes)

LOGOMATE offers 3 options for filtering SKUs in the node list.

1. Filter-Dialog

Classtree -> Rightclick “Filter” -> „Edit Filter“

In this window, you can set a temporary filter that will be reset the next time LOGOMATE is started.

You can filter by:

  • Columns from the node list
  • Parameters
  • Follow-ups
  • Actions
  • Planned values

At the top, you can also choose whether inactive SKUs should be included and whether upper- and lower-case letters should be taken into account in the entries.

2. Filter Class

Classtree -> Rightclick “Filter” -> „New Class“
Type: Filter class

The filter classes are permanently created, meaning that filter classes remain in the class tree even after LOGOMATE is restarted.

In addition, the “Global” checkbox can be used to decide whether the filter is accessible to everyone or only visible to yourself.

Another difference to the filter dialog is that there is now no limit to the number of columns that can be filtered.

It is also possible to create a filter class within a filter class. This allows filter groups to be created.

The final difference to the filter dialog is that the SKUs that end up in the filter can be parameterized. To do this, the filter must be selected when parameters are assigned.

3. Assignment Class

Classtree -> Rightclick “Filter” -> „New Class“
Type: Assignment Class

Assignment classes have all the functions that filter classes have, with one difference. Assignment classes are static because they are not filtered.

All desired SKUs that you want to have there are included.

Contracts

Contracts in LOGOMATE [Conditions/Parameters] are agreements between a supplier and a customer regarding the delivery of a specific SKU. The contract does not specify concrete delivery quantities or dates but merely defines the total quantity to be delivered within the agreed period (quantity contract).

The goods must be ready at any time at the specified time.

Customer contracts

Customer contracts do not specify a fixed date, but rather a delivery period.

Contract types

Ignore contracts

The contracts specified in the terms and conditions are ignored.

Favor Supplier

Supplier selection is based on the existing contract types. The time of availability is determined, with the underlying decision criterion defined in the “Contract selection” section.

Select Supplier

Suppliers are selected either on the basis of existing contracts or in accordance with the decision criteria specified in the section entitled “Select.”

Max. quantity

The maximum quantity that can be called off from the supplier.

Maximum quantity and supplier selection

The supplier is selected based on the maximum quantity that can be called up and the specified criteria for supplier selection.

Order splitting

If this option is enabled, order quantities for SKUs with multiple active suppliers can be split. The options Standing order and Order splitting are available, and both can be combined

Pseudo contracts

An additional SFT value can be specified for pseudo contracts. No customer number may be stored for this type of contract, as otherwise the “Delivered” field may be filled in automatically. Pseudo customer contracts imported from REMIRA do not contain the customer number, but the note “PSEUDO”.

Contracts at article level

An item can have multiple contracts, which are added in the Contracts tab of the Conditions window and automatically inherited by the associated SKUs.

SFT-Types

The safety stock level (SFT) is the minimum stock level required to avoid an out-of-stock situation. [Stock simulation]. Given the available parameters and conditions.

(The SFT is represented in LM by the blue dashed straight line.)

1. When stock is almost out of stock, the customer's usual order quantity is reordered.
2. Once the SFTis reached, an automatic reorder is triggered to replenish stock.
Common types
Effective: Standard deviation over the simulation period.
Effectively dynamic: : Here, the intervals are not considered directly in terms of months, as is the case with the effective interval, but rather the interval between the order date and the availability date (from the second order day).
Rare types
Minimal: Refers exclusively to Min.SFT(parameter) or 0 Dynamic: Increasingly refers to forecasting errors (frequent inaccuracy -> SFT monotonically increasing).
Max. departure: A daily sale is required here. Total expenditure in WBZ: Represents the sum of all departures during the WBZ.

Order-/Delivery Rhythm

An order or delivery rhythm is a regular series of orders or deliveries. This “series” can be set in the conditions window.

Order-Rhythm

If you select “Order” as the rhythm in the “Order Schedule” tab in the conditions window, an order rhythm is created, and orders are generated that are always placed within the defined period.

Delivery-Rhythm

If you select “Delivery” as the rhythm in the “Order Schedule” tab in the conditions window, a delivery rhythm is created, and orders are generated that are always delivered within the defined period.

Union Delivery / Order Rhythm

All order proposals for the next few days are summarized and proposed as a single order on the first order date. Unneeded SKUs are ordered in such a way that the rhythm of the Union is achieved.

Rhythm Assistant

The rhythm is configured using the Rhythm Assistant. Open the Rhythm Assistant by right-clicking in the lower area and then pressing “Insert”

The rhythm assistant consists of 10 sections

  1. Rhythm length: Which period size should be used for calculation
  2. Rhythm type: Which type of rhythm
  3. Order date: Date on which orders should always be placed + exception rule
  4. Transport/delivery date: : Date on which deliveries should always be made + exception rule
  5. Delivery time: Entered delivery time / new delivery time / exclusive delivery time
  6. All Interval between 2 orders
  7. If mandatory rhythm, rhythm start: Rhythm start is entered if the rhythm is to be maintained permanently, otherwise it can also be altered if LOGOMATE decides
  8. Based on: Specify which of the two rhythm types in section 7 applies
  9. Combined rhythm: Order proposals are combined and ordered according to a defined rhythm (section 7 must be empty)
  10. Validity range: Start & end of the rhythm

Predecessor

With a predecessor, the history is transferred from a predecessor SKU to a successor SKU. In addition, multiple time series can be linked.

A predecessor can be entered in LOGOMATE under the Tab “Miscellaneous” in the Parameters window

  • Copy the predecessor SKU from the node list and paste the SKU into the Predecessor field under the Tab “Miscellaneous” in the Parameters window.
  • Alternative: Search directly in the predecessor selection list. Partial entries are supported. In large systems, the partial article numbers must be precise enough to ensure that the results list does not become too large (up to 100,000 entries!).

In the forecast chart, the predecessor parts are highlighted in yellow

Precursor factors

Each historical value is multiplied by the predecessor factor:

  • Predecessor factor 1.0 = complete
  • Predecessor factor 0.5 = half
  • Predecessor factor 2.0 = double

Buffer store logic

With buffer store logic, additional warehouses are created in LOGOMATE. These can also be former branches or central warehouses that are no longer in operation.

The aim of these buffer stores is to use up their stock as quickly as possible.

This is implemented by transferring the demand from the active branches to the central warehouse. The central warehouse then primarily uses the buffer store stocks before accessing its own stocks.

Requirements

  1. The branch SKU must be transferred to both the central warehouse and the buffer store via the parts list with the type “Default” and assigned to the respective suppliers, whereby the suppliers of the buffer stores should be deactivated.
  2. The buffer store must receive the central warehouse SKU via the bill of materials with the type “buffer SKU” and must have the same supplier that was also transferred for the store SKU, but this time active. In addition, the “Type” parameter under the ‘Status’ tab must be set to “Forecast only, no MRP” and the SKU must be active.

If everything has been set up correctly, all store requirements should now be met primarily from the buffer stores. Only when the buffer stores are empty should the central warehouse meet the requirements with its stock.

If the buffer stock is not yet empty and the demand from the branches cannot be met at the desired times, the following procedures are applied, depending on the system settings:
[Note: Contact your REMIRA representative, who will set this up for you.]

Scenario „Cutbacks “:

Basic starting point:

In the “cutback” scenario, orders would be reduced so that each branch could be supplied with the remaining stock from one warehouse.

Note: The system parameter “partially unfulfillable branch order” must be set to “shorten.”

It would then look like this:

In the case of one-time calculations, an additional order for 30 items is created for the central warehouse in order to obtain the missing 30 items for the needs of the branches.

If a second calculation is performed or the system setting “Calculate twice if necessary” is activated, the export table looks as follows:

Branch 1 is reduced to 20 items because buffer store 2 has a stock of 20. Branch 2 is reduced to 10 units because buffer warehouse 3 has a stock of 10. Branch 3 will not be supplied because all buffer warehouses are empty and the central warehouse has more stock than Branch 3 needs.

Scenario „Splitting “:

Basic starting point:

In the “split” scenario, all stores would be supplied with existing stock, and the missing quantities would be reordered and delivered to the relevant stores.

Note: The system parameter “partially unfulfillable branch order” must be set to “split.”..

It would look like this:

Orders with shorter delivery dates are generally prioritized. In cases such as this, where all orders have the same delivery date, the SKU at the top is prioritized.

As a result, this means that...

Store 1 is first supplied from the buffer store and the remaining demand is covered by the central warehouse.
Branch 2 is supplied entirely from the central warehouse, as all buffer warehouses are empty.
Branch 3 is supplied with the remaining stock from the central warehouse, and the rest is delivered later by the central warehouse, which reorders the missing 30 items.

(From version 8.5-11) „Move“ scenario

Basic starting point:

In the “Move” scenario, the stocks would be distributed to the branches that can be supplied completely and most quickly.

Note:The system parameter “partially unfulfillable store order” must be set to “postpone.”

It would look like this:

After calculating with „splitting“:

Since branch LP92 has no stock, the central warehouse prefers to order LP92 and delivers its 2 items.
This means that the order from branch LP91 will be postponed until July 19, as the central warehouse first has to replenish its stock with an order.

Subsequent calculation with „Move“:

Since the order from branch LP91 can be fulfilled immediately, it will be given priority.

The delivery of the LP92 order will be postponed to July 18, as the central warehouse will have built up sufficient stock by then to fulfill this order, thanks to the delivery on July 16.
